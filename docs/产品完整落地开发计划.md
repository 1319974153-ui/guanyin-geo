## 1. 产品最终交付是什么

面向需要传播品牌的企业、个人、产品与服务经营者，交付可独立安装的观引桌面产品。客户使用自己的资料、模型服务和发布账号，不依靠 Codex 或开发者代填才能完成任务。

**首次使用：**输入品牌名 → 放入已有资料 → 一次确认品牌档案 → 连接写作模型 → 登录所需平台。

**日常使用：**点击“帮我写” → 从 4 个方向选一个 → 查看文章及重点修改意见 → 勾选平台发送 → 看各平台结果。

**优化效果：**查看 GEO 诊断 → 执行最重要的建议 → 主动复测 → 看同条件前后结果。

品牌名称本身不足以支持真实案例、数字和经营成果。系统可以整理已有官网或文档、建议待补材料；无法确认的内容先保留缺口。缺资料时仍应给出可用的收窄选题，避免把一张空白表交还给用户。

首个正式支持范围为 **Mac arm64 与 Windows x64 免插件桌面版**。Intel Mac、云端多人 SaaS 等单独扩展，不默认为已交付。客户自有模型与服务的费用归客户明确选择；软件包不附带开发者密钥、账号和客户数据。

完整落地的完成条件是：下方 G0～G6 全部通过，40 个任务的交付条件关闭，36 项目标逐一有准确结论。若平台客观不提供所需能力，保留事实、阻点和可替代方案，由用户决定是否调整范围；不能把该平台改成灰色后就宣称“全平台完成”。

可先交付明确支持范围的核心版供客户试用，但剩余平台仍继续记账，核心版不会被命名为本计划的全量完成。

## 3. 界面与操作标准

只保留三个主要入口：**工作台、文章与发布、GEO 诊断**。品牌资料、模型、账号和高级设置在需要时展开。

| 用户所处位置 | 默认看到什么 | 系统负责完成什么 |
| --- | --- | --- |
| 工作台 | 当前进度、最重要的下一步 | 汇总待确认文章、异常发布与前三项诊断建议 |
| 写文章 | 4 个不同方向、一句补充要求 | 复用资料、选择合适文体、带入来源和目标问题 |
| 看文章 | 正文、最多 3 项优先修改建议、确认按钮 | 事实风险定位、平台适配、原稿保存；其他问题展开查看 |
| 发布 | 平台勾选、账号名、一个发送按钮 | 检查所选平台必填项、串行或受控执行、回收结果 |
| 遇到本人验证 | 对应官方页面、当前任务说明 | 保留原稿和选择，完成后接续原任务；不让客户填任务编号 |
| GEO 诊断 | 当前观察、3 件最值得做的事、复测入口 | 保留口径、来源与历史，详细材料默认折叠 |

日常不能要求用户安装连接器、配对端口、手动核验账号、手动领取队列或复制回执。首次登录、平台强制验证、明确的费用和公开内容确认仍由本人完成，系统尽量合并成一次清楚的确认。

快捷选择不会收费；整次写作的范围、最多调用次数及预算提前说明。超出原范围需要再次确认。错误用业务语言说明发生了什么、保存了什么以及下一步入口。

## 5. 文章质量怎么做到可交付

### 5.1 资料一次导入

官网、文档和旧文章导入后提取候选事实，集中确认品牌归属、时间、数字、项目阶段、来源及公开范围。不同产品资料隔离，旧事实可更新，文章保留使用的事实版本。来源内容只作为资料，不作为产品执行指令。

资料不足时明确指出缺少哪项依据。例如缺客户评价时建议收集评价原文和使用授权；缺排名时建议查找原报告及时间、范围、口径。系统可以组织表达与材料获取建议，不能凭空制作已经存在的评价和排名。

### 5.2 问题与选题

问题来源分为真实咨询/搜索查询、用户录入、规则建议、模型候选。真实频次需带来源、时间窗和统计范围；候选优先级可以按业务相关性、资料支撑和覆盖缺口排序，但不能称为真实搜索概率。

每组 4 个方向要在读者需求、角度、资料使用或文章结构上有区别。方向卡说明“回答谁的问题、为什么写、用什么依据”，不只是四个近义标题。通用目标、文体和表达选项继续保留，默认交给 AI 推荐，用户可展开调整。

### 5.3 正文与质检

生成依据固定为当前品牌资料、目标问题、选定方向和文章类型。结构规则先检查格式、完整性与重复；语义审校再定位答非所问、标题未兑现、无支撑事实、过度宣传和文体偏离。若语义审校需模型调用，必须在本次写作预算里明确列出。

质检结果定位原句、依据和建议。涉及客户、数据、价格、能力、排名等关键品牌主张要能追溯；资料不充分时给更窄的表达或补资料动作。文章风险不能被一个高总分掩盖。

修改保留原稿、当前稿与修改理由；客户只说一句要求即可。正文或依据实质变化后旧发布批准失效。根据平台生成标题、摘要、正文、标签或图文卡片时保留底稿，不静默截断、删掉必要条件或串换图片。

### 5.4 真实质量验收

沿用现有《文章质量统一评审标准》，避免另设一套相互矛盾的评分。

- 六类品牌：消费品、餐饮本地门店、个人专业品牌、软件产品、制造 B2B、生活服务。
- 每类三项任务：默认推荐、明确文体、证据不足，共 18 项。
- 每项通过要求：总分 ≥80/100，真实性 ≥27/30，材料可核对 ≥12/15，无硬性失败；至少保留 3 段原文评审证据。
- 首次通过率和修复后通过率分别呈现；目标是减少客户改稿。最终 18 项均通过后关闭本组评测，任何事实或隐私硬性失败先修复再复验。
- “正确指出资料不足，并给可执行替代方向”可以合格，不强迫每项生成一篇长文章。
- 正常产品路径每项方向、正文各一次，18 项最多 36 次基础调用；分三批、每批六项安排。修改、审校、重试另计，均以实际预览和用户预算确认为准。不能将 18 项说成只有 18 次调用。
- 至少两类声明支持的模型服务验证连接、生成、用量与错误处理；其中一个固定模型版本跑完整 18 项，另一个做接口与代表场景兼容验收。更换主模型不沿用旧模型质量结论。
- 保存首次原始输出、版本、来源、错误和修改后结果；不挑最好一次覆盖失败。

这一组测试证明样本覆盖结果，不保证所有行业、所有模型或搜索排名效果。

### 每个目标统一验收卡

1. 当前版本、系统、正确账号和作者权限准确；首次登录后自动识别，过期只影响相应账号。
2. 关闭重开保留平台允许持久化的登录状态；重新登录后原稿、素材与平台选择保留。
3. 标题、完整正文、段落、声明、图片数量及顺序正确，必填项在发送前一次列出。
4. 平台支持草稿时保存可定位原稿，并重新打开核对；设备暂存明确标为设备暂存。
5. 获准的具体稿件一次提交，取得平台原稿/文章编号，不重复制造验收文章。
6. 审核中、驳回、待验证、结果未知和公开成功分开。公开成功需匹配的公开正文及链接；暂不可核验时不报成功。
7. 双击、断网、响应丢失、验证码、重启、账号变化不重复发；先找原任务。尚未发送的登记记录不能自动变为平台提交。
8. 至少一次三平台混合批次；一个平台待验证时，其余任务可独立推进，结果逐行显示。
9. 回执保存应用版本、平台账号、稿件/图片版本、动作、原稿编号、URL、时间及已知限制，并自动回到观引。

定时发布为高级可选功能，默认关闭，只发送客户明确批准的稿件与平台。时区、取消、错过时间和电脑休眠后恢复有确定规则；不主动每天调用收费模型，不集中补发漏掉的批次。客户端关闭时无法执行本机任务，要清楚提示。

## 7. GEO 诊断要解决什么

报告以“当前观察 → 最值得做的三件事 → 执行入口 → 复测比较”为主线。原始回答、统计口径和详细资料可展开查看。

- 区分提及、主动推荐、正文引用、参考列表与官网引用；无样本显示资料不足。
- 区分网站可访问、爬虫可抓取、搜索收录和模型实际引用，分别给检查建议。
- 真实样本保留问题版本、时间、模型/平台、入口、模式、地区、语言、原回答和来源；不能用网页 API 或模拟结果替代消费者回答。
- 豆包、元宝、千问至少各有一个同条件问题的基线与复测，共至少六条真实样本。出现零推荐仍可证明采样流程工作，不等于业务目标达成。
- 标签修改记录新旧值、操作者与时间，不伪装为新采样；历史报告不随标签或数据变化被悄悄改写。
- 建议关联对应产物：补资料关联事实版本、写稿关联已复核文章、发布关联实际回执、外部依据关联原材料、标签修复关联修改记录。
- 一键复测自动带出原条件；用户主动选择范围和费用。过时建议可停止或替代，停止不算已完成。
- 页面、归档、导出使用相同时间范围、分母与时区。当前 UTC 处理如需切换为用户本地时区，计算和筛选一并改，不能只改标签。
- 客户报告提供清楚的打印/PDF及现有结构化导出；分页、中文、长链接、大报告和空数据均验收。报告导出不含附件原件，必须与完整业务备份分开。

软件交付门槛是采样、分析、行动、发布和复测真实可用。AI 是否推荐某品牌、排在第几，需要持续观察真实结果，不写成软件保证。

## 8. 从预览版变为客户正式版

### 8.1 应用身份与升级

先固定正式应用名、唯一标识、版本、源码提交和数据位置。预览目录中的品牌、稿件、素材、任务、报告和设置先备份再迁移。能保留的登录态保留，平台不接受迁移的会话只提示该平台重新登录，不清空全部资料。

### 8.2 数据与故障

两套独立用户/工作区交叉检查模型密钥、平台会话、品牌、稿件、附件和发布队列。包内没有开发者路径、业务数据、实例编号和凭据。复核通用状态写入等历史路径，避免改稿后还能复用旧批准。

真实测试断网、模型超时、双击、取消、关窗口、重启、端口占用、磁盘写入失败和平台过期；要求不丢原稿、不自动重付费、不重复发文、不误报成功。完整备份可恢复附件和业务资料，报告导出不承担备份职责。

### 8.3 最终安装文件

Mac arm64 与 Windows x64 使用同一功能能力表。Windows 新增真正免插件 Electron 包，不依赖客户安装 Node 或浏览器扩展。

正式交付范围的功能完成并冻结后，才能关闭“最终安装文件”验收。前期核心版包可做阶段性试用，但不能代替全量范围的最终包。

对准备给客户的精确安装文件，在中文及空格路径、干净用户环境里完成：安装/解压 → 启动 → 完整业务主流程 → 退出重开 → 故障恢复 → 升级与回滚 → 卸载/清理。分别保存 Mac 和 Windows 真机回执，不能以开发服务通过代替。

运行时代码或打包配置随后变化时，旧最终包验收失效：重建安装文件与校验值，重新执行受影响检查。真实平台历史回执仅在对应适配器、能力门槛及运行环境仍适用并核对原结果后继承；不为重新打包而重复公开发布同一文章。

核对系统安全提示、签名与分发方式。如果所选正式签名方式需要账户或费用，先给出具体选择和成本，取得用户决定；不在客户包里留下绕过系统保护的含糊说明。

### 8.4 新客户试用与维护

邀请五名未参与开发的使用者，仅靠产品提示完成指定旅程，至少四名无需开发者代填。记录卡住的位置、重复输入、错误理解与时间。收费不明确、错账号、数据丢失、假成功、重复提交等阻断问题必须修复并复验。该门槛是交付样本检查，不推断全体客户表现。

产品提供一键脱敏诊断包、可操作错误提示、备份恢复入口、中文帮助、正常退出与卸载说明。平台变化时关闭受影响的未可靠动作，保留账号与原稿，显示验收版本和日期。

正式交付时 GitHub 源码、中文首页、版本说明、逐平台能力表、桌面应用版本、下载文件和 SHA-256 对应同一提交。保留安全回滚方式，不用未经验收的文件覆盖最新正式下载。

## 9. 如何高效推进

四条工作线并行，但真实浏览器只由一个执行者操作：

- 文章线：资料/模型连接 → 选题与事实 → 语义质检 → 平台适配 → 真实评测。
- 发布线：共同底座 → 六个历史渠道回归；公众号重点并行准备 → 四个核心公开闭环 → 其他适配器 → 十二项新渠道。
- 诊断线：标签审计与原条件复测 → 证据闭环 → 报告导出 → 真实样本比较。
- 交付线：正式身份与迁移先定 → Windows 免插件构建 → 隔离/恢复 → 固定安装文件 → 新客户试用 → 发布。

下一步优先：**Q07六类18任务真实模型质量评测与Q09真实服务/费用体验，核心平台及公众号当前版本真实验收，D06/D09/D10同条件消费端复测，I03/I05/I06正式安装包、迁移与Windows真机验收，再完成U02新客户独立试用和I04同版交付。** Q03来源溯源、Q08公开范围、U01三入口和标签闭环的已实现部分继续复用；新增变更重新测试与构建，技术执行仍由开发助手负责。

每批以可操作成果结束：改动清单、针对性测试、实际界面/平台/模型/安装包证据、更新的待办。没有新变化不反复汇报。平台验证或资格受阻时只请求那一次必要操作，继续不依赖它的开发。

本计划按完成关口排序，不用未经实测的日期承诺“全平台全部完成”。开发时间、平台审核等待、本人验证等待分开记录；首个真实质量批次与核心发布回归结束后，依据实际返工量再细化日历。

## 10. 用户需要配合的环节

1. **模型真实验收：**在产品内连接自有模型，确认一批调用和预算。密钥不发聊天；没有配置时继续离线开发。
2. **平台本人操作：**首次登录、扫码/短信、作者资格或绑定；系统保留原稿，不重复要求手动核验。
3. **公开验收：**确认可公开的具体稿件与目标账号；每个平台一次，有历史原任务先核对。
4. **额外条件：**相应的自建站/知识库、Windows 真机与新手试用；只有涉及新付费服务、账户权限或签名费用时再给出具体选择。

除此以外的开发、测试、资料整理和状态维护由开发执行方推进。不能承诺平台永不要求验证，也不让这些验证变成客户每天重复填表。
